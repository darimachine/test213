## 1. Основни понятия

> **Version control (контрол на версиите)** — система, която записва промените по файловете във времето, така че да можеш да се върнеш към стара версия.

> **Repository (хранилище, „репо“)** — проектът заедно с цялата му история. В Git това е скритата папка `.git/`.

> **Commit** — „снимка“ (snapshot) на проекта в даден момент + съобщение какво е променено.

> **Working Directory** — файловете, които виждаш и редактираш.

> **Staging Area** — „чакалня“, в която подбираш кои промени да влязат в следващия commit.

> **Untracked файл** — нов файл, който Git вижда, но още не следи.

> **Hash** — уникален идентификатор на commit, напр. `eb33de4`.

> **HEAD** — указател „къде съм в момента“.

> **Git** — програмата за контрол на версиите. Работи на твоя компютър.

> **GitHub** — сайт, на който качваш Git хранилищата си онлайн.

## 2. Защо ни трябва контрол на версиите

Всеки е виждал това:

```
📁 Курсова работа/
   ├── проект.docx
   ├── проект_v2.docx
   ├── проект_final.docx
   └── проект_final_v2_REAL_последен.docx
```

Тази папка **не може** да ти каже какво е различно между версиите, кой какво е променил и как да върнеш само една част от вчера.

**Контролът на версиите ти позволява да:**
- ✅ върнеш **избрани файлове** към предишно състояние;
- ✅ върнеш **целия проект** към предишно състояние;
- ✅ **сравниш промените** във времето;
- ✅ видиш **кой, кога и какво** е променил.

> 🎓 **Бележка за учителя:** Попитай: „Случвало ли ти се е да счупиш код, който вчера е работил, и да не знаеш какво си променил?“ — това е най-добрата мотивация.

## 3. Видове системи за контрол на версиите

### 3.1. Локален (Local)

Най-простото: **копираш файловете в друга папка**. Може и със специална програма (напр. RCS), която пази само разликите между версиите на диска.

**Проблеми:**
- лесно пишеш в грешния файл или в грешната папка;
- случайно презаписваш файлове;
- развали ли се дискът — губиш всичко;
- **няма съвместна работа** — всичко е на един компютър.

### 3.2. Централизиран (Centralised)

**Един сървър** пази всички версии, а програмистите теглят файлове от него. Примери: **CVS, Subversion (SVN), Perforce**.

```
          ┌──────────────────────┐
          │  Централен сървър    │
          │  (цялата история)    │
          └──────────────────────┘
            ▲        ▲        ▲
       ┌────┴──┐ ┌───┴───┐ ┌──┴────┐
       │ Ани   │ │ Боби  │ │ Вики  │
       │ само  │ │ само  │ │ само  │
       │текущи │ │текущи │ │текущи │
       │файлове│ │файлове│ │файлове│
       └───────┘ └───────┘ └───────┘
```

| ✅ Плюсове | ❌ Минуси |
|-----------|----------|
| Възможна е съвместна работа | **Single point of failure** — падне ли сървърът, никой не може да работи |
| Работата е синхронизирана | Изгори ли дискът на сървъра без backup — историята е загубена |
| Администраторите контролират кой какво може | |

> **Single point of failure** — едно място, чийто срив спира цялата система.

### 3.3. Разпределен (Distributed) — тук е Git

Примери: **Git, Mercurial, Bazaar, Darcs**.

Всеки програмист **копира цялото хранилище с цялата история**, а не само последните файлове.

```
               ┌───────────────────────┐
               │ Сървър (напр. GitHub) │
               │ ПЪЛНА история         │
               └───────────────────────┘
                 ▲         ▲         ▲
        ┌────────┴─┐ ┌─────┴────┐ ┌──┴───────┐
        │ Ани      │ │ Боби     │ │ Вики     │
        │ ПЪЛНА    │ │ ПЪЛНА    │ │ ПЪЛНА    │
        │ история  │ │ история  │ │ история  │
        └──────────┘ └──────────┘ └──────────┘
```

Какво печелим:
- **Всяко копие (clone) е пълен backup.** Падне ли сървърът, всеки може да го възстанови.
- Можеш да работиш **офлайн** — commit, история, всичко. Интернет ти трябва само за споделяне.
- Почти всичко е **бързо**, защото е локално.

### 3.4. Сравнение

| | Local | Centralised | Distributed |
|---|---|---|---|
| Примери | копиране на папки, RCS | CVS, SVN, Perforce | **Git**, Mercurial |
| Къде е историята | на един компютър | само на сървъра | **при всеки** |
| Съвместна работа | ❌ | ✅ | ✅ |
| Работа офлайн | ✅ | ❌ | ✅ |
| Ако сървърът падне | — | никой не работи | всички продължават |

> 🎓 **Бележка за учителя:** Аналогия: централизиран = една библиотека, от която всички взимат книги; разпределен = всеки има у дома **копие на цялата библиотека**.

## 4. Какво е Git

> **Git е разпределена система за контрол на версиите, която следи промените в кода по време на разработка.**

Защо се ползва (от лекцията):

| | |
|---|---|
| **Спестява време** | почти всичко е локално → бързо |
| **Работа офлайн** | commit и история без интернет |
| **Поправяне на грешки** | връщаш се към минало състояние |
| **Гъвкавост** | подходящ за всякакъв начин на работа в екип |

## 5. Git vs GitHub

Най-честото объркване при начинаещи — **това не е едно и също**.

| | **Git** | **GitHub** |
|---|---|---|
| Какво е | **Програма** | **Сайт / онлайн услуга** |
| Къде работи | На твоя компютър | В интернет |
| Трябва ли интернет | ❌ | ✅ |
| Какво прави | Следи версиите, прави commit-и, пази историята | **Пази хранилищата онлайн** + инструменти за екипна работа |
| Едното без другото | Git работи **без** GitHub | GitHub **без** Git няма смисъл |

> **Аналогия:** Git е **фотоапаратът** — с него правиш снимки на кода. GitHub е **Instagram / Google Photos** — там качваш снимките, за да са на сигурно и да ги споделиш.

**Какво добавя GitHub:**
- онлайн копие (**remote**) на проекта — backup и място за споделяне;
- удобно разглеждане на кода и историята в браузъра;
- **Pull Requests** и **Code Review** (урок 3);
- **Issues** — задачи и бъгове.

Слайдът *„Git didn’t beat SVN, GitHub did!“* означава: GitHub направи Git лесен за ползване онлайн и затова Git стана стандарт.

Подобни услуги: **GitLab**, **Bitbucket**. Командите на Git са едни и същи навсякъде.

## 6. Настройка — `git config`

Преди първия commit Git трябва да знае **кой си** — всеки commit записва име и имейл на автора. Без тях Git отказва да направи commit.

Проверка, че Git е инсталиран:

```bash
git --version
```

### 6.1. Трите нива

| Ниво | Флаг | Важи за |
|------|------|---------|
| **Local** | `--local` | само текущия проект |
| **Global** | `--global` | твоя потребител — всички твои проекти |
| **System** | `--system` | целия компютър (всички потребители) |

**Ако една настройка е зададена на няколко нива, печели най-конкретното:** local > global > system.

> 💡 Пример: глобално ползваш личния си имейл, а в служебния проект с `--local` слагаш служебния — само там ще се ползва той.

### 6.2. Първоначална настройка (веднъж на компютър)

```bash
git config --global user.name "Ivan Petrov"
git config --global user.email "ivan@example.com"
git config --global core.editor "code --wait"     # VS Code като редактор
```

> ⚠️ Сложи **същия имейл като в GitHub** — така GitHub свързва commit-ите с профила ти.

> 💡 `--wait` кара Git да изчака да затвориш VS Code, преди да продължи.

Проверка:

```bash
git config user.email        # една настройка
git config --list            # всички настройки
```

## 7. Ново хранилище — `git init` и папката `.git`

### 7.1. `git init`

```bash
mkdir git-demo
cd git-demo
git init
```

```
Initialized empty Git repository in /home/ivan/git-demo/.git/
```

Създаде се скрита папка **`.git/`**. **Тя е хранилището** — в нея Git пази цялата история.

> ⚠️ **Изтриеш ли `.git/`, изтриваш цялата история.** Файловете ти остават, но вече не са Git проект.

> 🎓 **Бележка за учителя:** Покажи, че `ls` не я показва, а `ls -a` — да (в Windows: *View → Hidden items*).

### 7.2. Какво има в `.git`

Не е нужно да се помни наизуст — важното е, че **всичко за историята е тук**.

| Част | Какво е |
|------|---------|
| **Objects** | Самите данни — commit-ите и съдържанието на файловете. Компресирани и именувани по hash. |
| **Refs** | Етикети, които сочат към commit-и (напр. клонът `main`). |
| **Logs** | За бързо показване на историята. |
| **Config** | Настройките на този проект (`--local`). |
| **Temp** | Временни файлове, които Git ползва между командите. |

Обектите са три вида:
- **blob** — съдържанието на един файл;
- **tree** — „папка“: кои файлове и подпапки има;
- **commit** — сочи към tree (цялото състояние) + предишния commit + автор + съобщение.

> ⚠️ Никога не редактирай файлове в `.git/` на ръка.

## 8. Трите зони на Git

**Най-важната идея в урока.** Всяка промяна минава през три места:

```
 ┌────────────────────┐   git add   ┌────────────────────┐  git commit  ┌────────────────────┐
 │ WORKING DIRECTORY  │ ──────────▶ │   STAGING AREA     │ ───────────▶ │    REPOSITORY      │
 │ файловете, които   │             │ какво ще влезе в   │              │ историята — всички │
 │ редактираш         │             │ следващия commit   │              │ commit-и           │
 └────────────────────┘             └────────────────────┘              └────────────────────┘
```

- **Working Directory** — папката с проекта. Всяка твоя промяна е тук веднага, но Git още **не я е записал**.
- **Staging Area** — тук слагаш промените, които искаш в следващия commit. Така можеш да групираш свързани промени: ако си оправил бъг и добавил бутон, правиш **два отделни** commit-а вместо един общ.
- **Repository** — записаните commit-и. От тях винаги можеш да възстановиш състояние.

> **Аналогия — пазарска количка:** `git add` = слагаш в количката, `git commit` = плащаш на касата. Докато не си платил, можеш да добавяш и вадиш.

## 9. `git status` и untracked файлове

`git status` показва **какво е променено, какво е в staging и кои файлове са нови**. Не променя нищо — пускай го постоянно.

```bash
echo "# Моят проект" > README.md
echo 'print("Hello")' > app.py
git status
```

```
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	README.md
	app.py
```

Състоянията, които ще виждаш:

| Секция в `git status` | Значение |
|-----------------------|----------|
| `Untracked files` | нови файлове, Git не ги следи |
| `Changes not staged for commit` | променени, но **не** добавени със `git add` |
| `Changes to be committed` | в staging — ще влязат в следващия commit |

> 💡 `git status` винаги подсказва в скоби какво да направиш — свикни да ги четеш.

**Untracked файлове:** Git знае, че съществуват, но **никога не ги е записвал**. Ако изтриеш такъв файл — **не може да се възстанови**.

> 📝 В слайда подсказките са `git reset HEAD <file>` и `git checkout -- <file>`. Новите версии на Git показват `git restore --staged <file>` и `git restore <file>`. Правят същото.

## 10. `git add` — добавяне в staging

`git add` слага промени в **staging зоната**. ⚠️ Той **не записва** нищо в историята — това става едва при `git commit`.

```bash
git add <file>        # един файл
git add <directory>   # цяла папка
git add .             # всичко в текущата папка
```

```bash
git add README.md
git status
```

```
Changes to be committed:
	new file:   README.md

Untracked files:
	app.py
```

`README.md` е в staging, `app.py` — още не.

**Махане от staging** (промяната във файла остава):

```bash
git restore --staged README.md
```

> 💡 Преди `git add .` пусни `git status` — да не добавиш нещо, което не искаш (временни файлове, пароли). За това служи `.gitignore`.

## 11. `.gitignore`

### 11.1. Какво е

Файл `.gitignore` в корена на проекта, в който изреждаш кои файлове Git да **игнорира** — да не ги показва и да не ги добавя.

Какво обикновено се игнорира:
- компилирани файлове — `.class` (Java), `.pyc` (Python), `.exe`;
- изтеглени библиотеки — `node_modules/`;
- билд папки — `build/`;
- **пароли и ключове** — `.env`.

```gitignore
# всички файлове с това разширение
*.class
*.tmp

# цяла папка
build/
node_modules/

# тайни — никога в Git
.env
```

Демо:

```bash
touch notes.tmp
git status              # notes.tmp се вижда като untracked
echo "*.tmp" > .gitignore
git status              # notes.tmp изчезна
```

> 💡 Самият `.gitignore` се commit-ва, за да важи за целия екип. Готови шаблони има при създаване на repo в GitHub.

### 11.2. ⚠️ Капан

`.gitignore` важи **само за файлове, които още не са commit-нати**. Ако файлът вече е в Git, трябва изрично да спреш да го следиш:

```bash
git rm --cached secret.env     # маха го от Git, файлът остава на диска
```

## 12. `git commit` и правила за съобщенията

### 12.1. Какво прави

`git commit` записва **всичко от staging** като нов commit — снимка с уникален hash, автор, дата и съобщение.

```bash
git commit -m "Add README"
```

```
[main (root-commit) 2470626] Add README
 1 file changed, 1 insertion(+)
```

- `2470626` — краткият hash на commit-а.
- `root-commit` — първият commit в проекта.

### 12.2. Правила за кратко съобщение

1. **Повелително наклонение** — като команда: **Add**, **Fix**, **Update**, **Remove** (не „Added“, „Fixing“).
2. **Главна буква** в началото.
3. **До 50 символа.**

> 💡 Съобщението трябва да довършва изречението: *„If applied, this commit will ___“* → „…will **Fix login error**“ ✅

| ❌ Лошо | ✅ Добро |
|---------|----------|
| `fix` | `Fix crash when list is empty` |
| `changes` | `Add email validation to signup` |
| `Added stuff and fixed bugs` | две отделни съобщения за два commit-а |

Пример от лекцията:

```bash
git commit -m "Update default policies for KVM guest PIT & RTC timers"
```

### 12.3. Заглавие + описание

Когато 50 символа не стигат, пускаш `git commit` **без** `-m` — отваря се редактор:

```
Refactor libvirt create calls                       ← заглавие (до 50 символа)
                                                    ← ВИНАГИ празен ред
- Minimize duplicated code for create               ← описание: какво и защо
- Make wait_for_destroy happen on shutdown
```

- Редът между заглавието и описанието **винаги е празен** — така Git ги разделя.
- Описанието може да е на точки или обикновен текст.
- Редовете с `#` се игнорират; празно съобщение отказва commit-а.

> ⚠️ Ако не си настроил редактор, често се отваря **Vim**. Изход: `Esc` → `:wq` → `Enter` (запиши) или `Esc` → `:q!` → `Enter` (откажи).

> 🎓 **Бележка за учителя:** В GitHub Desktop полетата **Summary** и **Description** са точно заглавие и описание — покажи го, правилото става визуално.

## 13. `git log` — историята

```bash
git log
```

```
commit eb33de4ce54c55b38eb071a8e811d1f9aa32d529 (HEAD -> main)
Author: Ivan Petrov <ivan@example.com>
Date:   Sun Nov 22 23:57:15 2026 +0200

    Add hello app

commit 2470626d874774d52eb7fa12e2b9c6b32a238660
Author: Ivan Petrov <ivan@example.com>
Date:   Sun Nov 22 23:57:15 2026 +0200

    Add README
```

- Най-новото е **най-отгоре**.
- `(HEAD -> main)` — тук сме в момента.
- Излизаш с `q`.

Полезни варианти:

```bash
git log --oneline     # по един ред на commit
git log --graph       # рисува историята като граф (вижда се при клонове — урок 2)
```

```
eb33de4 Add hello app
2470626 Add README
```

**Красивият log от лекцията** — правим го на съкращение (alias), за да не се пише всеки път:

```bash
git config --global alias.lg "log --graph --pretty=format:'%Cred%h%Creset -%C(yellow)%d%Creset %s %Cgreen(%cr) %C(bold blue)<%an>%Creset' --abbrev-commit"
git lg
```

```
* eb33de4 - (HEAD -> main) Add hello app (3 seconds ago) <Ivan Petrov>
* 2470626 - Add README (3 seconds ago) <Ivan Petrov>
```

## 14. Как „мисли“ Git

1. **Всеки commit е пълна снимка** на проекта. Непроменените файлове не се копират отново — просто се преизползват.
2. **Commit-ите са верига** — всеки сочи към предишния:

```
  (2470626) ◀──── (eb33de4)
  Add README      Add hello app
                       ▲
                      main
                       ▲
                      HEAD
```

3. **`main`** е етикет към последния commit. **`HEAD`** показва къде си ти. При нов commit и двата се местят напред.
4. **Hash-ът е пръстов отпечатък** — промениш ли нещо в commit, получаваш друг hash.

**Ежедневният цикъл:**

```
редактираш → git status → git add → git commit -m "…" → git log
```

## 15. GitHub — демо: от локален проект до GitHub

> 🎓 **Бележка за учителя:** Remote командите се учат подробно в урок 2. Тук показваш само минимума, за да види студентът проекта си в GitHub.

### 15.1. Акаунт

На **github.com → Sign up**, със **същия имейл** като в `git config`.

### 15.2. Ново repo в GitHub

1. Горе вдясно **„+“ → New repository**.
2. Име: `git-demo`. Public или Private.
3. ⚠️ **Не** отмятай *Add a README / .gitignore / license* — нашият проект вече има история и двете ще се разминат.
4. **Create repository**.

### 15.3. Вход от терминала

GitHub **не приема паролата на акаунта** от терминала. Най-лесно:
- **Windows** — при първия `git push` се отваря прозорец за вход (Git Credential Manager);
- **Mac/Linux** — `gh auth login` (GitHub CLI);
- или се логваш в **GitHub Desktop**.

### 15.4. Качване (push)

```bash
git remote add origin https://github.com/<username>/git-demo.git
git branch -M main
git push -u origin main
```

| Команда | Какво прави |
|---------|-------------|
| `git remote add origin <url>` | Запомня адреса на GitHub repo-то под името `origin` |
| `git branch -M main` | Уверява се, че клонът се казва `main` |
| `git push -u origin main` | Качва commit-ите. `-u` запомня връзката — следващия път стига `git push` |

### 15.5. Разглеждане в GitHub

Презареди страницата:
- виждаш файловете — а `notes.tmp` **липсва**, защото е в `.gitignore`;
- `README.md` се показва като начална страница на проекта;
- **„commits“** → историята, като `git log`;
- клик на commit → какво е променено (зелено/червено).

### 15.6. Оттук нататък

```bash
git add <файлове>
git commit -m "Describe the change"
git push
```

> 🎓 **Бележка за учителя:** Направи една промяна → commit → push и презареди GitHub пред студента. Това затваря кръга.

## 16. Същото в GitHub Desktop и VS Code

| Действие | Терминал | GitHub Desktop | VS Code |
|----------|----------|----------------|---------|
| Име и имейл | `git config --global …` | *File → Options → Git* | ползва глобалния config |
| Ново repo | `git init` | *File → New repository* | *Source Control → Initialize Repository* |
| Статус | `git status` | таб **Changes** | панел **Source Control** (Ctrl+Shift+G) |
| Stage | `git add` | **отметката** пред файла | бутон **+** |
| Unstage | `git restore --staged` | махаш отметката | бутон **−** |
| Commit | `git commit -m` | **Summary** + **Description** → *Commit* | поле за съобщение → **✓ Commit** |
| История | `git log` | таб **History** | разширение **Git Graph** |
| Игнориране | `.gitignore` | десен клик → *Ignore file* | десен клик → *Add to .gitignore* |
| Първо качване | `remote add` + `push -u` | **Publish repository** | **Publish Branch** |
| Push | `git push` | **Push origin** | **Sync Changes** |

> 💡 В GitHub Desktop staging зоната е „скрита“ зад отметките. Затова е добре първо да се види в терминала.

## 17. Чести грешки

| Ситуация | Какво става | Решение |
|----------|-------------|---------|
| Commit без име/имейл | `Please tell me who you are` | `git config --global user.name/email` |
| Commit без нищо в staging | `nothing to commit` | първо `git add` |
| Команда извън Git папка | `fatal: not a git repository` | `cd` в правилната папка или `git init` |
| Файл в `.gitignore`, но още се следи | `.gitignore` не важи за commit-нати файлове | `git rm --cached <file>` + commit |
| Промяна след `git add`, после commit | влиза версията **от момента на `add`** | `git add` отново |
| Празна папка не се вижда | Git следи файлове, не папки | сложи файл вътре (напр. `.gitkeep`) |
| Заседнал във Vim | — | `Esc` → `:wq` или `:q!` |
| Паролата не минава при push | GitHub не приема парола | вход през прозореца / `gh auth login` / GitHub Desktop |
| `push` → `rejected` | в GitHub има commit, който нямаш (напр. README) | `git pull` — урок 2 |

## 18. Cheat sheet

```bash
# Настройка (веднъж)
git config --global user.name "Име Фамилия"
git config --global user.email "email@example.com"
git config --list

# Ново хранилище
git init

# Работен цикъл
git status
git add <file>              # или: git add .
git restore --staged <file> # махане от staging
git commit -m "Summary"
git commit                  # заглавие + описание в редактор

# История
git log
git log --oneline
git log --graph

# Игнориране
# .gitignore → *.tmp, build/, .env
git rm --cached <file>

# GitHub
git remote add origin <url>
git branch -M main
git push -u origin main     # първия път
git push                    # после
```

**Commit съобщение:** повелително наклонение · главна буква · до 50 символа · празен ред преди описанието.

## 19. Въпроси за проверка

**1. Каква е разликата между Git и GitHub?**
<details><summary>Отговор</summary>
Git е програма на компютъра ти. GitHub е сайт, който пази Git хранилища онлайн и добавя инструменти за екипна работа.
</details>

**2. Какъв е основният минус на централизираните системи?**
<details><summary>Отговор</summary>
Single point of failure — падне ли сървърът, никой не може да работи.
</details>

**3. Защо при Git всяко копие е пълен backup?**
<details><summary>Отговор</summary>
Защото всеки копира цялото хранилище с цялата история.
</details>

**4. Кое ниво на `git config` печели — local или global?**
<details><summary>Отговор</summary>
Local — по-конкретното ниво печели.
</details>

**5. Какво става, ако изтриеш `.git`?**
<details><summary>Отговор</summary>
Губиш цялата история. Файловете остават.
</details>

**6. Кои са трите зони и с кои команди минаваме между тях?**
<details><summary>Отговор</summary>
Working Directory → git add → Staging Area → git commit → Repository.
</details>

**7. Записва ли `git add` нещо в историята?**
<details><summary>Отговор</summary>
Не, само слага промяната в staging. Записва се при `git commit`.
</details>

**8. Защо е рисковано да изгубиш untracked файл?**
<details><summary>Отговор</summary>
Git никога не го е записвал и не може да го възстанови.
</details>

**9. Сложил си файл в `.gitignore`, но той още се показва. Защо?**
<details><summary>Отговор</summary>
Защото вече е бил commit-нат. Трябва `git rm --cached <file>`.
</details>

**10. Поправи съобщението „fixed bug“.**
<details><summary>Отговор</summary>
Напр. „Fix crash on empty cart“ — повелително, с главна буква, конкретно, до 50 символа.
</details>

**11. Какво задължително има между заглавието и описанието на commit?**
<details><summary>Отговор</summary>
Празен ред.
</details>

**12. Какво е HEAD?**
<details><summary>Отговор</summary>
Указател къде си в момента — обикновено към текущия клон и последния му commit.
</details>

## 20. Упражнения и куиз

**Упражнение 1 — Настройка.** Настрой име и имейл (същия като в GitHub) и ги провери с `git config --list`.

**Упражнение 2 — Първи commit.** Създай папка `my-notes`, направи `git init`, създай `README.md`, пусни `git status`, добави го и направи commit.

**Упражнение 3 — Трите зони.** Създай `todo.txt` и `ideas.txt`. Добави **само** `todo.txt` и виж `git status`. Направи commit. После commit-ни `ideas.txt` в **отделен** commit.

**Упражнение 4 — `.gitignore`.** Създай `debug.log` и папка `build/` с файл вътре. Направи `.gitignore`, така че да не се виждат в `git status`. Commit-ни `.gitignore`.

**Упражнение 5 — Съобщения.** Поправи: `fixed the bug`, `changes`, `Added login page and fixed header`. Направи един commit със заглавие + празен ред + описание (`git commit` без `-m`).

**Упражнение 6 — История.** Направи още няколко commit-а, разгледай ги с `git log`, `git log --oneline` и с alias-а `git lg`.

**Упражнение 7 — GitHub.** Създай празно repo `my-notes` в GitHub, качи проекта с `git push -u origin main`, провери в GitHub файловете и commit-ите. Направи още една промяна → commit → `git push`.
